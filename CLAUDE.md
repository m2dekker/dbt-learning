## How to teach (agreed working style)
- One step at a time. Before each step: 2–4 sentences on what and why it matters in real projects.
- Run setup commands myself, but show the command and explain it.
- After each step, STOP and wait for "next" or questions.
- At key moments (✍️), Mike writes the model/test first; review it like a senior analytics engineer.
- Every few steps (❓), ask 1–2 quick questions to check understanding.
- When something fails, explain the error before fixing it — reading dbt errors is a skill to build.

## Conventions agreed
- Python deps pinned in `requirements.txt`.
- Git: private remote https://github.com/m2dekker/dbt-learning (branch `main`).
  Claude commits + pushes at the end of each step ("Step N: ...").
- Ignored by git: `.venv/`, `target/`, `dbt_packages/`, `logs/`, `*.duckdb`.
- Seeds = stand-in for EL-loaded raw data: `seeds/raw_<entity>.csv`, generated by `scripts/generate_seeds.py` (random.seed 42), loaded into schema `main_raw` (`+schema: raw`).
- Amounts in raw data are integer cents.
- Staging grouped by source system: `models/staging/<source>/`; source YAML named `_<source>__sources.yml`. Source name = `shop`.
- Only staging models call `source()`; everything downstream uses `ref()`.
- Staging: `stg_<source>__<entities>.sql`, materialized as view (folder default). CTE pattern: `source` → `renamed` → (`deduplicated`) → `select *`. Keys renamed to `<entity>_id`. Columns grouped by ids / strings / numerics / booleans / timestamps.
- Only the key carries the entity prefix (`customer_id`); other columns stay plain (`email`, not `customer_email`).
- Dedupe versioned rows with `order by updated_at desc` (keep latest).
- Generic attribute names (`name`, `status`, `category`, `type`) DO get the entity prefix (`product_name`, `order_status`) — ambiguous after joins / reserved words.
- Timestamps named `<event>_at` (`ordered_at`, `paid_at`). Amounts stay in cents in staging until the cents_to_dollars macro (step 11).
- Packages: `packages.yml` uses version ranges; `package-lock.yml` is committed. Generate staging drafts with
  `dbt run-operation codegen.generate_base_model --args '{"source_name": "shop", "table_name": "raw_x"}'`, then hand-finish.
- Model docs/tests in `_<source>__models.yml` per folder; use `data_tests:` + `arguments:` (dbt 1.10+ style).
- Data-quality policy: known, meaningful source issues → keep rows, `severity: warn` + `store_failures: true`
  (failing rows land in `main_dbt_test__audit`, shareable with source owner). Money columns use thresholds
  (`warn_if: ">0"`, `error_if: ">10"`). Zero-quantity lines to be filtered in intermediate layer.
- Known planted issues: order 150 → customer 999; order line 77 null product_id; line 200 qty 0; payments 60 & 180 null amount.
- Fabric note: DuckDB `qualify` is not valid T-SQL → use CTE + `where rn = 1`.

## Concepts Mike struggled with
- Custom schema naming (`main` + `raw` → `main_raw`, developer isolation). Revisit `generate_schema_name` in Fabric phase.
- Step 5 review of stg_shop__customers: single vs double underscore in model name; copied instead of moved
  file (→ duplicate model); trim placed on wrong column; country codes lowered instead of ISO upper;
  `order by` without `desc`. Also: dbt never drops orphaned objects after rename/delete.
- Step 6: accepted_values typo (spaces vs underscores, missing value) — profile distinct values first with `dbt show --inline`.
  Test names sanitise spaces → trust compiled SQL. Data-quality handling: tended to one-size-fits-all; differentiate by risk.
- "Transform" ≠ staging: staging = one table, row-level, no joins/aggregations/business logic.
